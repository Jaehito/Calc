# 기능 검증 체크리스트 아티팩트

**무엇을 확인해야 하는지**를 사용자가 직접 눌러 지워가는 목록을 만든다. 테스트를 돌리는 스킬이 아니다 — 테스트로는 못 잡는 것(화면·연출·입력)과 판단이 필요한 것을 골라내는 것이 목적이다.

## 대상 대화 정하기

기본은 **이 스킬을 호출한 대화**다. 사용자가 다른 대화를 지목하면 (`"그룹없음 에이전트 대화"`, `"유물 작업한 대화"` 등) 그 대화를 읽는다.

1. `mcp__ccd_session_mgmt__list_sessions` 로 제목·최근 활동을 본다. 제목이 애매하면 워킹 트리 변경 파일과 대조해 고른다.
2. 전사 읽기는 `list_events` 보다 **jsonl 직접 읽기가 싸다**. `~/.claude/projects/C--UnityProjects-SOS/*.jsonl` 중 최근 수정본을 첫 사용자 메시지로 식별한다 (CCD `sessionId` 와 파일명은 다르다).
3. **턴별 마지막 assistant 텍스트**만 뽑으면 완료 보고가 거기 다 있다. 1000+ 메시지 세션도 이 방식이면 한 번에 읽힌다.

```python
# 턴별 (사용자 요청, 그 턴의 마지막 assistant 텍스트) 추출
def texts(c):
    if isinstance(c, str): return c
    if isinstance(c, list): return '\n'.join(x.get('text','') for x in c if isinstance(x,dict) and x.get('type')=='text')
    return ''
```

⚠️ **콘솔에 한글을 직접 출력하지 않는다** — mojibake가 된다. UTF-8 파일로 쓰고 `Read` 도구로 읽는다 (`.claude/rules/table-ssot-drive.md` 와 같은 함정).

## 항목 뽑기 — 전사와 diff를 대조한다

전사만 읽으면 대화에 안 나온 변경을 놓치고, diff만 보면 "이 클래스가 무슨 기능이냐"가 안 나온다. **둘 다 본다.**

- 전사 → 무엇을 하려 했는지, 무엇을 통과라고 보고했는지, 무엇을 미검증이라고 스스로 인정했는지
- `git status` / `git diff` → 실제로 바뀐 파일, 새로 생긴 클래스·테스트·`.asset`
- **어긋나면 그게 최우선 항목이다.** "통과 보고"와 "실제 상태"가 벌어지는 자리에서 사고가 난다 (실측 사례: 45종 동작 보고 → 실제 39종. 버프를 컨테이너에 넣는 것과 그 버프를 읽는 코드가 있는 것을 혼동한 것)

## 분류 — 확인 필요도 순 3단

| 묶음 | 들어가는 것 | 열림 |
|---|---|---|
| **① 화면으로만 확인 가능** | 연출·레이아웃·입력 경로·잘림 — EditMode가 원리적으로 못 잡는 것 | 펼침 |
| **② 통과했지만 다시 볼 가치** | 집계·수치가 한 번 틀렸던 자리, 기획 판단이 걸린 자리, 조건이 구조적으로 성립 안 할 위험이 있던 자리 | 펼침 |
| **③ 통과 · 잡을 것 없음** | 지정 실행해 통과 보고된 것 | **접힘** |

- **미구현은 목록에 넣지 않는다** — 확인할 것이 아니라 만들 것이다. footer에 한 줄로 적는다.
- 항목이 30개를 넘어도 이 구조를 유지한다 (③이 접혀 있어 화면이 안 늘어난다).

**배지 어휘 5개** — 이것만 쓴다.

| 배지 | 뜻 |
|---|---|
| `미확인` | 눌러보면 답이 나온다 |
| `확인 불가` | 지금 확인할 수단이 없다 (해당 유물/카드가 없는 등). 체크 대상으로 만들지 말고 이유를 적는다 |
| `재확인` | 통과 기록은 있지만 값을 직접 세어볼 가치가 있다 |
| `판단 필요` | 동작이 아니라 기획 결정이 필요하다 |
| `통과` | 그 대화가 지정 실행해 통과 보고했다 |

## 항목 한 줄에 담는 것

**이름 + 확인 방법(재현 절차)** 둘뿐이다. 테스트 이름·파일 경로·커밋은 넣지 않는다 (`통과` 항목의 테스트 수치는 확인 방법 자리에 적는다).

확인 방법은 **눌러야 하는 순서**로 쓴다 — `F1 → 유물 탭 → [단일] 검은 넥타이 적용 → 덱 탭 C3_Spade → 전투 진입 → HIT로 스페이드를 놓는다 → 방패 안 숫자가 커지면 통과`. 무엇이 통과인지 마지막에 붙인다.

## 정직성 (강함)

- 체크박스는 **전부 빈칸**으로 낸다. 내 판정은 색과 배지로만 표시한다 — 사용자가 확인한 것과 내가 판정한 것을 섞지 않는다.
- 테스트 결과를 옮길 때는 **"그 대화가 실행해 보고한 기록이며 내가 다시 돌린 것이 아니다"** 를 상단에 명시한다. 재실행하려면 `.claude/rules/playtest.md` 의 승인 절차를 따로 밟는다.
- 화면 미검증을 "통과"로 올리지 않는다. 스크린샷이 발동 프레임만 잡았으면 그건 `미확인`이다.

## 발행

`template.html` 을 스크래치패드로 복사해 채우고 `Artifact` 로 발행한다.

- `capabilities: {"artifact": {}}` — 이게 있어야 체크가 남는다
- **`data-id` 를 `<input>` 자신에 붙인다** (load-bearing). 런타임이 `[data-id]` 를 찾아 `checked` 를 되돌려주므로, `<li>` 에만 있으면 체크가 복원되지 않는다. `<li>` 와 값이 겹치지 않게 `chk-` / `row-` 로 접두사를 가른다
- 스크립트가 그리는 것(집계·진행률)은 **`<artifact-local>` 안에** 둔다. 제스처 없이 스크립트가 만든 마크업은 저장되지 않고, 그런 요소가 있으면 그 뷰의 저장이 꺼진다
- favicon·title 은 재발행 때 바꾸지 않는다

## 갱신 (두 번째 호출부터)

1. 그 대화가 이미 발행한 URL을 찾는다 (없으면 `Artifact` `action: "list"`, 그래도 없으면 사용자에게 링크를 묻는다).
2. **`WebFetch` 로 현재 HTML을 읽어 `checked` 가 붙은 `data-id` 를 모은다.** curl은 SPA 껍데기만 받는다 — `WebFetch` 를 쓴다.
3. 새 항목을 추가하고, 모은 `data-id` 에 `checked` 를 복원해 같은 파일 경로(또는 `url`)로 재발행한다.

**id는 문구가 바뀌어도 바꾸지 않는다.** 내용이 갱신된 항목은 같은 id로 문구만 고친다 (id가 낡아 보여도 그대로 — `count-44-51` 이 48/51을 담고 있어도 바꾸지 않는다). 해당 없어진 항목은 지우지 않고 `class="row retired"` 로 그 자리에 남긴다. 새로 들어온 항목은 `class="row fresh"` 로 금색 띠를 준다.

footer에 이번 갱신에서 무엇이 새로 들어오고 무엇의 내용이 바뀌었는지 한 줄 적는다.
